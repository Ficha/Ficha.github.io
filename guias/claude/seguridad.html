Una revisión de seguridadA security review

Cómo le pido a Claude que revise mis proyectos, qué conviene buscar y qué no conviene contar.How I ask Claude to review my projects, what's worth looking for and what's better left unsaid.

Cuando una app la hacés vos con Claude, la seguridad es tuya. No hay un equipo que la revise antes de publicar: estás vos, Claude y una tarde. Mis apps son chicas (un diario, un juego de misiones, una app para la carrera, este sitio), pero tienen datos de otras personas, y eso ya alcanza para tomárselo en serio.

Así que de vez en cuando le pido a Claude una revisión de todos mis proyectos. La primera vez encontró cosas en cinco. Ninguna grave, todas de las que se arreglan en una tarde si alguien las mira.

Qué buscar

  • Pedidos de cualquier origen. Un formulario o un servidor local que acepta órdenes de cualquier página, cuando solo debería aceptarlas de la propia.
  • Código en línea. Si una página permite scripts escritos dentro del HTML, un texto inyectado puede ejecutarse. Para eso existe la política de seguridad de contenidos (CSP, por su sigla en inglés), que solo deja correr los scripts propios.
  • Claves y contraseñas en el repositorio o en su historial. Borrarlas del archivo no alcanza: si estuvieron en un commit, hay que cambiarlas.
  • Versiones sin fijar. Dependencias y acciones de GitHub que su autor puede cambiar por debajo.
  • Datos que no hace falta guardar. El dato más seguro es el que no tenés.

Cómo pedirla

  • Primero, solo lectura. Que liste los hallazgos con gravedad, archivo y línea, sin tocar nada.
  • Arreglar de a uno, cada arreglo en su rama y en una carpeta aparte (un worktree), para no pisar otras sesiones.
  • Para lo que cambiaste hace poco está /security-review, que revisa los cambios pendientes de una rama antes de publicarlos.

Las copias también cuentan

Si hacés copias automáticas de tus proyectos, que un freno busque claves y contraseñas en lo que va a subir, y que no suba nada si encuentra una. Que el destino sea privado no es excusa: privado no quiere decir seguro.

Lo que no se cuenta

Esta tarjeta no dice qué encontró Claude en mis proyectos ni qué falta arreglar. No es pudor. Un hallazgo abierto contado en público es una invitación. Los hallazgos van a un archivo privado y se cuentan, si acaso, cuando ya están cerrados y no dicen nada útil para nadie con malas intenciones.

El prompt

Hacé una revisión de seguridad de este proyecto, solo de lectura. Buscá: formularios o servidores que acepten pedidos de cualquier origen, código en línea que permita inyectar scripts, claves o contraseñas en el repositorio o en el historial, dependencias y acciones de GitHub sin versión fija, y datos de personas que se guarden sin necesidad. Para cada hallazgo, decime la gravedad (alta, media o baja), el archivo, la línea y una corrección propuesta. Anotalos en un archivo que no se publique. No cambies nada todavía; después los arreglamos de a uno, cada uno en su rama.

When you build an app yourself with Claude, security is on you. There's no team reviewing it before it goes live: there's you, Claude and an afternoon. My apps are small (a journal, a quest game, an app for my degree, this site), but they hold other people's data, and that's enough to take it seriously.

So every now and then I ask Claude for a review of all my projects. The first time it found things in five. None serious, all the kind that gets fixed in an afternoon if someone looks.

What to look for

  • Requests from any origin. A form or a local server that accepts orders from any page, when it should only accept them from its own.
  • Inline code. If a page allows scripts written inside the HTML, injected text can run. That's what a content security policy (CSP) is for: it only lets the site's own scripts run.
  • Keys and passwords in the repository or its history. Deleting them from the file isn't enough: if they were ever in a commit, change them.
  • Unpinned versions. Dependencies and GitHub actions their author can change underneath.
  • Data you don't need to keep. The safest data is the data you don't have.

How to ask for one

  • First, read-only. Have it list findings with severity, file and line, without touching anything.
  • Fix them one at a time, each fix on its own branch and in a separate folder (a worktree), so you don't step on other sessions.
  • For recent changes there's /security-review, which reviews a branch's pending changes before you publish them.

Backups count too

If you make automatic copies of your projects, have a brake look for keys and passwords in what's about to be uploaded, and upload nothing if it finds one. The destination being private is no excuse: private doesn't mean safe.

What isn't told

This card doesn't say what Claude found in my projects or what's left to fix. It's not modesty. An open finding told in public is an invitation. Findings go to a private file and get told, if at all, once they're closed and say nothing useful to anyone with bad intentions.

The prompt

Do a read-only security review of this project. Look for: forms or servers that accept requests from any origin, inline code that allows script injection, keys or passwords in the repository or its history, dependencies and GitHub actions without a pinned version, and personal data stored without need. For each finding, give me the severity (high, medium or low), the file, the line and a proposed fix. Write them to a file that doesn't get published. Don't change anything yet; we'll fix them one at a time afterwards, each on its own branch.
