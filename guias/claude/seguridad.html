Una revisión de seguridadA security review

Un repaso de todos mis proyectos con Claude, y lo que encontró en apps que hice yo.A pass over all my projects with Claude, and what it found in apps I built myself.

Cuando una app la hacés vos con Claude, la seguridad es tuya. No hay un equipo que la revise antes de publicar: estás vos, Claude y una tarde. Mis apps son chicas (un diario, un juego de misiones, una app para la carrera, este sitio), pero tienen datos de otras personas, y eso ya alcanza para tomárselo en serio.

El 14 de noviembre le pedí a Claude una revisión de todos mis proyectos. Encontró cosas en cinco.

Lo que encontró

  • Un panel local que aceptaba cualquier pedido. Una herramienta mía para limpiar carpetas recibía órdenes de cualquier origen. Ahora exige que el pedido venga de la propia página, en el formato esperado, y revisa a qué dirección llega.
  • Scripts escritos dentro del HTML. Si una página permite código en línea, un texto inyectado puede ejecutarse. La solución es una política de seguridad de contenidos (CSP, por su sigla en inglés) que solo acepte los scripts propios.
  • Acciones de GitHub sin fijar. Los flujos que publican el sitio usaban versiones que su autor podía cambiar por debajo. La corrección es apuntar a una versión exacta.

El primer arreglo ya está publicado. Los otros dos están en una rama, sin publicar: antes quiero probar a mano las apps que tocan.

Secretos fuera del backup

Tengo un backup diario de mis proyectos en un repositorio privado. Antes de cada copia, un freno busca contraseñas y claves en lo que va a subir; si encuentra una, no sube nada. Además, el backup deja afuera las transcripciones de Claude y los archivos de configuración con claves. Que el repositorio sea privado no es excusa: privado no quiere decir seguro.

Cómo pedirla

  • Primero, solo lectura. Que liste hallazgos con gravedad, archivo y línea, sin tocar nada.
  • Arreglar de a uno, cada arreglo en su rama y en una carpeta aparte (un worktree), para no pisar otras sesiones.
  • Para lo que cambiaste hace poco está /security-review, que revisa los cambios pendientes de la rama antes de publicarlos.

El prompt

Hacé una revisión de seguridad de este proyecto, solo de lectura. Buscá: formularios o servidores que acepten pedidos de cualquier origen, código en línea que permita inyectar scripts, claves o contraseñas en el repositorio o en el historial, dependencias y acciones de GitHub sin versión fija, y datos de personas que se guarden sin necesidad. Para cada hallazgo, decime la gravedad (alta, media o baja), el archivo, la línea y una corrección propuesta. No cambies nada todavía; después los arreglamos de a uno, cada uno en su rama.

When you build an app yourself with Claude, security is on you. There's no team reviewing it before it goes live: there's you, Claude and an afternoon. My apps are small (a journal, a quest game, an app for my degree, this site), but they hold other people's data, and that's enough to take it seriously.

On November 14 I asked Claude for a review of all my projects. It found things in five.

What it found

  • A local panel that accepted any request. A tool of mine for cleaning up folders took orders from any origin. Now it requires the request to come from its own page, in the expected format, and checks which address it arrives at.
  • Scripts written inside the HTML. If a page allows inline code, injected text can run. The fix is a content security policy (CSP) that only accepts the site's own scripts.
  • Unpinned GitHub actions. The workflows that publish the site used versions their author could change underneath. The fix is pointing to an exact version.

The first fix is already live. The other two are in a branch, unpublished: first I want to test by hand the apps they touch.

Secrets out of the backup

I have a daily backup of my projects in a private repository. Before each copy, a brake looks for passwords and keys in what's about to be uploaded; if it finds one, nothing goes up. The backup also leaves out Claude's transcripts and config files with keys. The repository being private is no excuse: private doesn't mean safe.

How to ask for one

  • First, read-only. Have it list findings with severity, file and line, without touching anything.
  • Fix them one at a time, each fix on its own branch and in a separate folder (a worktree), so you don't step on other sessions.
  • For recent changes there's /security-review, which reviews a branch's pending changes before you publish them.

The prompt

Do a read-only security review of this project. Look for: forms or servers that accept requests from any origin, inline code that allows script injection, keys or passwords in the repository or its history, dependencies and GitHub actions without a pinned version, and personal data stored without need. For each finding, give me the severity (high, medium or low), the file, the line and a proposed fix. Don't change anything yet; we'll fix them one at a time afterwards, each on its own branch.
